# Ingest via MCP: operating pattern (zero cost)

## TL;DR for the developer

The MCP server does **not** expose (and should not expose) filesystem
operations on the middleware's `data/` directory. There are two MCP-native
ways to load content, plus a third operational way for large files. This
document explains when to use which, why we did not add file CRUD to the MCP
tools, and which shell step the "large file" case requires.

---

## The gap that showed up in production

An MCP-only agent that already has a JSON file of chunks ready (e.g.
generated by a preprocessing script) cannot write it into `data/` with the
MCP tools. `qdrant_ingest_file` reads only files already present under
`middleware-qdrant-manager/data/`, and the MCP server has no tool to stage
files there. Result: the agent has to "leave" MCP and use the host shell to
copy the file, then come back to MCP for the ingest.

**This is intentional and must stay that way.** The rest of this document
explains why, and the correct pattern.

---

## The three ingest paths

### Path 1 — `qdrant_ingest_chunks` (MCP-native, inline)

For modestly sized content already available in the agent's memory/context.

```json
qdrant_ingest_chunks {
  "source_id": "manual-v1",
  "collection_name": "docs",
  "chunks": [
    {"id": 1, "text": "Qdrant stores vectors.", "lang": "en"},
    {"id": 2, "text": "The middleware embeds text before writing.", "lang": "en"}
  ]
}
```

- No file on disk, no shell step.
- `source_id` is required (there is no file name to derive it from).
- Fields constant across all chunks can go in `metadata` (e.g.
  `{"author": "...", "work": "..."}`) to reduce the payload size.
- **Real limit**: 4 MiB per request, imposed by the MCP server's
  streamable-HTTP transport `max_request_body_size`, *before* the tool runs —
  the agent gets a transport-level rejection with no tool-level message to
  explain it (the 413 branch in `errors.py` is never reached in this case).
  It is **not** the middleware's body size: `REQUEST_BODY_MAX_BYTES` is
  26_214_400 bytes (25 MiB) by default, a threshold that is never reached
  when going through MCP.
- **Practical limit, lower than the previous one**: inline chunks pass
  through the agent's context window. A ~1.3 MB corpus would fit within the
  4 MiB, but inlining it becomes impractical long before it is too large. At
  that scale use Path 3, or split across several `qdrant_ingest_chunks`
  calls sharing the same `source_id`.

### Path 2 — `qdrant_ingest_file` (MCP-native, file already staged)

For files already present under the middleware's `data/` (e.g. loaded by the
deploy, by a CI pipeline, or staged manually by the operator).

```json
qdrant_ingest_file {
  "file_path": "corpus/manual.json",
  "collection_name": "docs"
}
```

- `file_path` is relative to `middleware-qdrant-manager/data/`.
- A path that resolves outside `data/` (absolute, or `..` segments climbing
  out) is rejected with HTTP 400 (sandbox).
- Default `source_id` = file name without extension.
- The file must already exist: the MCP tool does **not** create it.
- At most `INGEST_MAX_CHUNKS` chunks per call (10000 by default) and
  `INGEST_MAX_FILE_BYTES` per file (64 MiB by default). Over the chunk cap is
  HTTP 413, which this server reports as `Error: request body too large.`;
  over the byte cap is HTTP 400 `File too large`. Both caps apply to every
  ingest call, Path 1 included for the chunk count.

### Path 3 — Large file + explicit shell step (operational)

For large files generated outside the middleware. This is the pattern to
document as an "operating procedure" in agent-facing runbooks.

**Step 1 — prepare the file** (host side, outside MCP):
the JSON file must have a top-level `chunks` array:
```json
{ "chunks": [ {"id": 0, "text": "...", ...}, ... ] }
```

**Step 2 — copy into `data/`** (host shell, NOT an MCP tool):
```powershell
$dst = "<repo>\middleware-qdrant-manager\data\corpus"
New-Item -ItemType Directory -Path $dst -Force | Out-Null
Copy-Item "<source path>\file.json" -Destination "$dst\file.json" -Force
```
On Linux/macOS:
```bash
mkdir -p "<repo>/middleware-qdrant-manager/data/corpus"
cp "<source path>/file.json" "<repo>/middleware-qdrant-manager/data/corpus/file.json"
```

**Step 3 — ingest via MCP**:
```json
qdrant_ingest_file {
  "file_path": "corpus/file.json",
  "collection_name": "docs",
  "source_id": "file",
  "batch_size": 8
}
```

The shell step is **explicit and visible**: it is not hidden behind an MCP
tool, so the operator knows they wrote to `data/` and stays responsible for
what ends up there.

## Real example followed in this project

Ingest of *I Promessi Sposi* (39 chapters, ~220k words, ~1.3 MB JSON):

1. A Python script `build_promessi_sposi_chunks.py` generates
   `promessi_sposi_chunks.json` on the user's desktop.
2. The shell (PowerShell) copies the file to
   `middleware-qdrant-manager/data/corpus/promessi_sposi_chunks.json`.
3. `qdrant_ingest_file` with `file_path: "corpus/promessi_sposi_chunks.json"`,
   `source_id: "promessi-sposi"`, `batch_size: 8` → 39 chunks ingested.

No MCP tool for step 2, and that is correct.

## Why we do NOT add file CRUD to the MCP tools

### 1. The `data/` mount is read-only inside the container
```
"Source":"...\\middleware-qdrant-manager\\data","RW":false
```
An MCP write tool would require flipping the mount to RW, weakening a
hardening the project deliberately maintains (non-root container UID/GID
1000, read-only root filesystem). It must not be reversed for convenience.

### 2. Layer violation
The MCP server is defined as a "thin, stateless translation layer" that
exposes the middleware's REST API. The host filesystem is not part of the
middleware's REST API — it is deployment operations. Mixing the two turns
the MCP server from a pure proxy into a file manager as well: two
responsibilities, two attack surfaces.

### 3. Expanding the MCP token's blast radius
Today a compromised `MCP_API_TOKENS` does damage on Qdrant (serious, but
recoverable from backup). With file CRUD, the same token becomes filesystem
write/delete on the host. The delete is irreversible: no undo, no recycle
bin. It is the same reasoning behind the `confirm` gate on `replace_source`
and `recreate=true`: destructive operations are made hard on purpose.

### 4. Path traversal is the classic bug
`ingest_file` already validates paths (paths escaping `data/` are rejected
with 400), but on a read-only surface. A general CRUD multiplies the chances
of getting the validation wrong — and a path traversal in a write tool is an
RCE-shaped vulnerability, not a minor bug.

### Note — `qdrant_export_collection` (2026-08-07)

The four arguments above remain valid: they are written against a
caller-driven file CRUD tool. The native export was evaluated against all
four and passes them:

1. **RW mount** — it does not touch `data/`, which stays `:ro`. It writes to
   a dedicated `exports/` mount.
2. **Layer** — the `POST /points/export` endpoint makes the write part of the
   middleware's REST API, performed by the service that already owns that
   filesystem. The MCP server remains a pure proxy.
3. **Blast radius** — no path, filename or content from the caller, no
   delete, no overwrite outside `exports/`. A compromised token can consume
   disk with dumps of collections it could already read via
   `qdrant_scroll_points`.
4. **Path traversal** — not applicable: no caller input reaches the path.

Details: "Export a whole collection" in
[`../../middleware-qdrant-manager/README.md`](../../middleware-qdrant-manager/README.md)
and the `qdrant_export_collection` row in [`../README.md`](../README.md).

### 5. `qdrant_ingest_chunks` already covers the MCP-native case
There is no *capability* gap: there is a *convenience* gap for large files.
For inline content there is already `ingest_chunks`. The "large file already
prepared" case is an operational case for the user, not for the agent — and
it is right that it stays operational (shell, scp, deploy scripts).

## Where this pattern is documented

The content has been integrated in five places, in order of reachability
for an MCP-only agent:

1. **`docs://workflows/ingest`** (live MCP resource, section "Staging a file
   this server cannot write") — the main surface: discoverable via
   `mcp_read_resource` without any access to the repo.
2. **The server's `instructions`** (`smart_qdrant_mcp/server.py`) — the
   4 MiB ceiling and the pointer to the resource, delivered in the
   `initialize` handshake, so seen before any tool description.
3. **The `qdrant_bootstrap_collection` prompt** (`smart_qdrant_mcp/prompts.py`,
   step 5) — the "file not yet staged" case and its two fallbacks.
4. **`smart-qdrant-mcp-server/README.md`**, section "Ingest" — the complete
   copy + ingest example, for those reading the repo.
5. **`smart-qdrant-mcp-server/README.md`**, section "Operational limits" —
   the 4 MiB ceiling already documented there before this plan (it was
   correct before too: it was not touched, only confirmed).

## If the friction becomes significant in the future

Evaluate (in increasing order of cost):

1. **Nothing** — keep the operating pattern above. Cost: zero.
   Benefit: zero friction for the cases already covered.
2. **A narrow write-only tool** `stage_ingest_file(path, content)` with
   paranoid validation (path relative to `data/`, no `..`, no absolute paths,
   `.json` extension, size limit, no overwrite without `confirm`). Covers 90%
   of the need without granting list/delete. **It still requires the RW
   mount** — the hardening cost is there all the same.
3. **An endpoint in the middleware** (not in MCP) `POST /ingest/stage` that
   writes into `data/` with the sandbox that already exists. MCP stays a pure
   proxy. This too needs the RW mount.

**Never add** an arbitrary delete or list on `data/` via MCP: the
benefit/risk ratio is clearly unfavourable.
