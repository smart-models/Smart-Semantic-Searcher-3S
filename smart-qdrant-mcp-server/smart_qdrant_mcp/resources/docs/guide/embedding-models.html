01 / Before the model names

One switch.
Three jobs to fill.

A profile is a fixed set of models that together do everything the stack needs from machine learning. Both profiles fill the same three roles.

Role 1 / Dense embedding

Turn a passage into meaning.

The dense model reads a passage and produces one fixed-length vector of 1024 numbers. The model is trained to place related texts close together, including texts that share no words; relevance still needs evaluation on your corpus. Your question is embedded the same way, so “rotate the credential” may find “replace the token”.

Stored in Qdrant as the dense vector
Role 2 / Sparse embedding

Keep lexical evidence.

The sparse model produces a vector of weights over a vocabulary: non-zero entries carry lexical evidence, and the remaining entries are zero. This can help retrieve variable names, error codes and rare jargon, but tokenization and learned weights do not guarantee literal matching. The two profiles fill this role differently. BGE-M3 weights the tokens that actually appear in the text. MILCO projects the text onto an English pivot vocabulary and can also weight terms the text never spells out, a learned expansion that helps across languages. Neither is an exact-match filter; for hard constraints on metadata, use payload filters.

Stored in Qdrant as the sparse vector
Role 3 / Reranking

Give the shortlist a second look.

After Qdrant fuses the dense and sparse candidates, the reranker reads your question together with each candidate passage and scores the pair. It is slower per passage, so it only sees the shortlist; it never touches the whole collection.

Runs at query time only; nothing is stored

Why the profile is chosen once.

  1. One line in .env. SMART_EMBEDDER_PROFILE is basic or advanced. Any other value stops Smart Embedder at startup instead of guessing. The shipped template selects advanced; basic is what the server falls back to when the variable is absent.
  2. Read at process start. The models load once and stay resident. There is no runtime switch: changing the family means restarting the stack, which the CLI guide walks through.
  3. Stamped at creation. When the app creates a collection it records an embedding-contract fingerprint of the active profile in the collection’s metadata, before any vector is written. Every vector that later lands there is shaped by exactly these models, and only these models can search them. See what that means for you ↓.
Same size is not the same space

Both profiles produce 1024-number dense vectors, and both store one sparse vector per passage. That does not make them interchangeable. A BGE-M3 vector and a Qwen3 vector for the same sentence are points in two unrelated coordinate systems; comparing them would produce unreliable relevance scores. The contract check exists so that this never happens silently.

Where the text can be cut

  1. Admission: body, entry count and request budgets can reject work before inference.
  2. Embedding: each backend applies its own tokenizer and window. The dense and sparse cut points can differ.
  3. Retrieval: Qdrant returns candidate payload text; the embedding window does not shorten the stored payload.
  4. Reranking: the middleware trims surrounding whitespace, then takes the first 1000 Unicode characters of each candidate by default. The reranker then tokenizes the query and candidate within its own window.

02 / The basic profile

Basic.
One family does everything.

Two model repositories from the Beijing Academy of Artificial Intelligence. One encoder produces every vector type; a sibling reranker built on the same encoder scores the shortlist.

When you would choose it

A useful baseline for a first run or a policy that forbids custom model-repository Python. One encoder supplies both retrieval vectors. CPU startup uses a smaller embedding window; memory needs also depend on batch size, input length and concurrency. See the recorded hardware evidence below.

SMART_EMBEDDER_PROFILE=basic

One encoding, two retrieval signals.

Model capability

The third output / ColBERT

Token vectors are a separate design choice.

ColBERT keeps a vector for each token and compares the query and passage through late interaction. BGE-M3 can produce it; the middleware always sends return_colbert: false.

This project uses dense + sparse retrieval followed by a reranker. Storing token vectors would add storage and a separate scoring path. The project has not measured a ColBERT quality gain over this pipeline on its own corpora.

Why this choice, and how to request ColBERT

Qdrant documents a multi-stage design that retrieves candidates cheaply, then rescores with multivectors. Token vectors in that design can omit HNSW indexing. This supports a storage and complexity tradeoff, not a claim that ColBERT is worse than a cross-encoder. Qdrant: multivectors and late interaction ↗.

For your own integration, call Smart Embedder’s POST /embeddings/ directly under basic with return_colbert: true. Publish its host port, provide its bearer token when authentication is enabled, and handle storage/search yourself. Advanced rejects return_colbert: true.

{
  "sentences": ["Rotate the API token every 90 days."],
  "return_dense": true,
  "return_sparse": true,
  "return_colbert": true,
  "sparse_as_indices": true
}

A direct request in the basic profile. The app itself always sends return_colbert: false.

03 / The advanced profile

Advanced.
Three specialists, one roster.

A Qwen3 encoder for meaning, a research model for multilingual sparse retrieval, and a Qwen3 reranker that judges each pair. Each was chosen for one job.

When you would choose it

The shipped template’s default, worth evaluating for multilingual retrieval and longer dense inputs on GPU. On CPU its dense context is capped while MILCO retains a larger sparse window. MILCO executes pinned custom model code. The launcher’s automatic choice is a hardware heuristic, not a quality or memory guarantee.

SMART_EMBEDDER_PROFILE=advanced
Dense / Role 1

Qwen/Qwen3-Embedding-0.6B

Long context, when the runtime allows it.

Model capability
A 0.6B Qwen3 model supports 32K input tokens, task instructions and Matryoshka Representation Learning (MRL): output dimensions from 32 to 1024.
Used in this stack
The stack always keeps 1024 dimensions. A search query is embedded with the model’s own query instruction; stored text carries none. GPU defaults allow the full window; CPU defaults cap it. MRL is not exposed as a setting.
Practical impact
A long model context is not the CPU input limit. Published evaluations do not establish this stack’s quality; compare the actual pipeline on your data.

Choose basic when

You want the simplest trustworthy start.

A first run, a smaller GPU or none at all, or a policy that forbids third-party model code. One family and native architecture support. Measure its recall, latency and memory as your baseline.

Choose advanced when

Your documents are long or multilingual.

On GPU, the larger dense window can help with long inputs, while MILCO adds a shared lexical space across languages. On CPU, dense still has the smaller cap. Measure whether these differences help your queries.

Let the launcher decide when

You are not sure what the machine can carry.

up auto inspects local NVIDIA devices and applies one threshold to the selected GPU: the one named with --gpu-device or STACK_GPU_DEVICE, otherwise the one with the most total memory. 7680 MiB or more picks advanced, less picks basic, and no device means CPU. A model named on the command line always wins over the automatic result. This total-memory threshold does not measure free VRAM or predict retrieval quality.

Upstream specification
The model cards above link to immutable README revisions. They support architecture, dimensions and declared capabilities. Their benchmark results describe their own evaluation setup.
Stack behaviour
The profile reference, runtime controls and middleware settings describe what runs here. Model pins live in model_revisions.py; CPU/GPU defaults are checked against compose.yml.
Measured evidence
The embedder’s recorded hardware baselines report particular machines and workloads. They do not prove a universal VRAM bound or that one profile retrieves better.
Teaching examples

Compare the profiles on your own corpus
  1. Freeze the task. Use identical source texts, chunk boundaries, metadata and filters. Prepare a small pilot of representative questions with human relevance judgments, including identifiers, paraphrases, your language pairs and long-passage failures. Reserve held-out questions before tuning.
  2. Build separate collections. Import the same chunks under each profile and record their fingerprints. Keep retrieval depth, fusion, rerank window, character cap and Qdrant settings equal for the first comparison.
  3. Measure both stages. Record candidate Recall@k (relevant passages retrieved divided by all judged relevant passages) before reranking, then nDCG@10 (graded relevance discounted by position, normalized to the ideal ranking) after reranking. Report the cutoff, relevance scale, unanswered queries and judgment coverage. A reranker cannot repair missing candidates.
  4. Measure cost separately. Report warm p50/p95 end-to-end query latency, ingest throughput and peak memory under a fixed concurrency and input-length distribution. Separate cold preparation from warm serving. Record hardware, model revisions, runtime, precision, limits and truncation warnings.
  5. Choose from the tradeoff. Inspect failures per language and query type, not only an overall mean. Tune on the development questions, freeze settings, then evaluate once on the held-out set. A small pilot is a starting point, not statistical proof of a winner.

The embedder benchmark measures service performance; it does not supply corpus relevance judgments or this end-to-end retrieval evaluation. Keep the questions, judgments, configuration and results together so someone else can repeat your comparison.

05 / One contract per collection

The vectors remember
who made them.

Switching profiles is a restart away. Making an existing collection follow is not, and the app refuses to pretend otherwise.

  1. The stamp. Smart Embedder reports an embedding_contract_fingerprint for the active profile. The middleware writes it into the collection’s metadata when it creates the collection, before the first vector arrives.
  2. The check. Import, vector upsert and search compare the running profile with the collection’s stamp. A mismatch is refused with an HTTP 409 embedding-contract error. Results are never silently mixed across vector spaces. Re-embed is the migration path: its preflight checks whether the existing collection can be regenerated for the active target contract. The job keeps that target stable and updates the collection’s contract after regeneration and verification.
  3. Three ways forward. Restart the stack under the collection’s original profile, which touches no data. Regenerate every vector under the new profile with Collections → Re-embed Vectors in the console, when its read-only preflight says the collection is ready. Or create a new collection under the new profile and import the source texts again, often the clearest route when the preflight says no.
Plan the family before the first import

Re-embedding processes every stored passage again; budget time and compute for the whole collection. Decide between basic and advanced on a small sample of your own documents, keep that choice in .env, and treat a later change as a migration. 06 / Common questions

Answers about
the models themselves.

For startup errors, use the CLI guide. For search quality, use the hybrid search guide. These questions are about what the models are and do.

Can I plug in a different model?

Not through configuration. The two profiles are fixed rosters, pinned to exact Hugging Face commits, and the autotuner, the request limits and the embedding contract are all built around them. A different model is a code change to Smart Embedder with a new pinned revision and a new smoke-test pass, not a setting.

What you can choose is the profile, the hardware and the runtime controls listed in the basic and advanced configuration references.

Do my documents or questions leave my machine?

Not for embedding or reranking. Every model on this page runs inside the Smart Embedder container on your CPU or GPU, and the only network the models need is the first download of the pinned weights from Hugging Face into the local cache volume.

Storage is a separate question. Your passages, their payloads and their vectors are sent to the Qdrant instance named in QDRANT_URL. If that is a remote or cloud Qdrant, they leave your machine at that step even though the embedding itself stayed local. Likewise, if you connect an AI agent that uses a cloud model, your questions and the returned passages can cross that boundary on the agent’s side. A local Qdrant and a local agent are what keep the whole flow on your own infrastructure; the architecture guide shows where the line sits.

Can I get ColBERT vectors for my own project?

Yes, in the basic profile, by calling Smart Embedder directly with return_colbert: true. You need the published host port, a Smart Embedder bearer token when authentication is enabled, and your own storage; the middleware and the console will not store or search those vectors. Read why the stack leaves them out ↑.

Why did my scores change after switching profile?

Because the rerankers speak different languages. The BGE reranker scores with a logit, sigmoid-normalized to 0–1 by default; the Qwen reranker returns a yes-probability. Both can read 0–1, but they are not on a shared scale. Fused retrieval scores also come from different vector spaces. Compare rankings and the passages they surface, not the numbers between profiles.

Both profiles produce 1024 numbers. Are they compatible?

No. Equal length is a coincidence of two model designs, not a shared geometry. A collection stamped by one profile is refused by the other with a 409 error until you restore its profile or complete a compatible re-embed migration; a new collection and reimport is another route. The contract section explains the three ways forward.

What happens to a passage longer than the model’s context?

Once a request is admitted, a passage over the context limit is truncated to it, and the response carries a structured input_truncated warning naming the passage and how much was cut. Admission comes first: a request body over the size cap, too many entries, or a batch whose estimated work exceeds the request budget is refused with HTTP 413 before any model runs. The limits are per model, not per profile. On CPU the shipped Compose caps the dense encoders at 2048 tokens in both profiles (set in .env by BGE_EMBED_CPU_MAX_LENGTH and QWEN_EMBED_CPU_MAX_LENGTH, not by the GPU-side *_EMBED_MAX_LENGTH), while MILCO’s sparse branch keeps MILCO_MAX_LENGTH at 8192, so under advanced the two vectors of one passage can be cut at different points. For search quality, split long documents into passages well below the smallest limit before import.

The first start is slow. Is that the models?

Mostly. The first preparation downloads the selected profile’s pinned snapshots, then the autotuner measures runtime candidates on your hardware and saves a decision. Later starts reuse both. The CLI guide explains the preparation pause and the quick, full and off calibration modes.

What does “trust remote code” mean for MILCO?

The MILCO repository ships Python that defines its architecture, and loading it executes that code inside the Smart Embedder container. The stack contains the risk: the snapshot is pinned to one immutable commit, model preparation refuses any snapshot whose revision differs, and the container runs read-only as a non-root user. The basic profile has no such path. If your policy rules out third-party model code, that is the deciding factor, not performance. Read the full note ↗.
